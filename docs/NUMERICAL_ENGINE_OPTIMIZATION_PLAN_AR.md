# خطة تحسين المحرك العددي والتدريب في SkeAI

> النطاق: الفرع `feat/cpp-training-core`، مع الحفاظ على صحة التدريب والتوافق مع Termux/Android. هذه الخطة لا تعتبر أي تحسن أداءً حقيقيًا قبل قياسه على الجهاز المستهدف.

## 1. الوضع الحالي الذي بُنيت عليه الخطة

- تخزين Tensor رقمي متصل ومملوك لـ C++ في `cpp/skeai_engine.cpp`، مع غلاف API في `src/skeai/engine.py`.
- مسار تدريب Transformer مجمّع في C++ عبر `transformer_train_step` و`transformer_train_batch`، مع مخزن ذاكرة تدريب محلي للخيط.
- ضرب المصفوفات العام `cpp_matmul` يستخدم حاليًا ترتيب حلقات row → k → column، وهو ترتيب جيد نسبيًا للتخزين row-major لأن المرور على أعمدة الناتج متصل في الذاكرة، لكنه لا يطبق tiling.
- دالة `TinyTransformerLM._forward_cached` في `src/skeai/level2/transformer.py` ما زالت تحتوي عمليات حسابية ونسخًا إلى قوائم Python. لا ينبغي افتراض أن تحسين `cpp_matmul` وحده يسرّع مسار التدريب المدمج أو مسار الاستدلال؛ يجب قياس كل مسار منفصلًا.
- Level 2 يستخدم `token_embedding` و`position_embedding` ومعرّفات tokens، وليس One-hot بحجم السياق × المفردات. لذلك يجب حماية التصميم الحالي، وفحص ما إذا كانت أي مسارات قديمة أو تجارب أخرى ما زالت تنشئ One-hot كثيفًا.

## 2. قواعد السلامة قبل التغيير

1. الاحتفاظ بنواة مرجعية Baseline لا تتغير نتائجها، واستخدامها لاختبار جميع النوى الجديدة.
2. فصل تغييرات الأداء عن تغييرات الخوارزمية أو إعدادات التدريب؛ لا تغيّر حجم النموذج ومعدل التعلم وطريقة التحديث مع تحسين GEMM في نفس التجربة.
3. مقارنة النتائج العددية باستخدام سماحية مطلقة ونسبية موثقة، لا اشتراط التطابق البتي عندما يغيّر ترتيب الجمع.
4. تشغيل الاختبارات أولًا، ثم benchmark دافئ مع عدة تكرارات، وعرض الوسيط (median) إلى جانب أقل/أعلى زمن.
5. عدم استبدال المسار المرجعي تلقائيًا إذا فشلت الاختبارات، أو كانت المكاسب أصغر من ضوضاء القياس، أو تراجع تدريب النموذج كاملًا.

## 3. مراحل التنفيذ

### المرحلة A — تثبيت Baseline واختبارات صحة النوى

**الهدف:** الحصول على مرجع موثوق قبل تحسين الأداء.

- الاحتفاظ بنواة GEMM الحالية باسم واضح مثل `matmul_baseline`، وعدم حذفها بعد إضافة نواة محسنة.
- اختبار الأبعاد الصغيرة وغير المتوافقة وحدود الـ tiles، مثل: (1×1)×(1×1)، و(2×3)×(3×4)، وأبعاد لا تقبل القسمة على 16 أو 32، والمصفوفات المتوسطة والكبيرة.
- فحص الأبعاد السالبة، وفائض حساب عدد العناصر، وأحجام التخزين غير المطابقة، والمخرجات غير المنتهية إن كانت ضمن عقد الـ API.
- إجراء اختبار مقارنة بين baseline والنواة الجديدة باستخدام بيانات حتمية وقيم موجبة وسالبة وأحجام متنوعة.
- إضافة اختبار خطوة تدريب حتمية يقارن loss والأوزان بعد التحديث، وليس الـ forward فقط.

**بوابة القبول:** جميع الاختبارات الحالية والجديدة تمر، ولا يظهر اختلاف خارج السماح العددي المعتمد.

### المرحلة B — ترتيب الحلقات وTiling وSize-based Dispatch

**التطبيق المقترح:**

- للمصفوفات الصغيرة استخدم baseline مباشرة؛ كلفة اختيار النواة والتقسيم قد تفوق فائدتها.
- للمصفوفات الكبيرة أضف نواة tiled بتحريك كتل الصفوف والأبعاد الداخلية والأعمدة.
- اجعل حدود الكتل ثابتة مبدئيًا (مثل 16 أو 32) ثم قارنها على Android؛ لا تفترض أن حجمًا بعينه هو الأفضل لكل CPU.
- اختر النواة بناءً على أبعاد M وK وN وحجم العمل M×K×N، وليس على عدد العناصر وحده فقط. استعمل حسابًا آمنًا من overflow عند حساب حجم العمل.
- ابدأ بعتبة dispatch مؤقتة قابلة للضبط، ثم اختر قيمتها من نتائج benchmark على الجهاز المستهدف، وسجّلها مع تقرير القياس.

المقطع التالي **هيكل توضيحي** لتقسيم GEMM، وليس استبدالًا جاهزًا قبل ربطه بعقد الدوال والاختبارات الموجودة في الملف:

~~~cpp
using index_t = std::size_t;

// All tensors are row-major. A is MxK, B is KxN, C is MxN.
// C must be zero-initialized exactly once before accumulation.
void matmul_baseline(
    const double* A, const double* B, double* C,
    index_t M, index_t K, index_t N
) {
    std::fill(C, C + M * N, 0.0);
    for (index_t i = 0; i < M; ++i) {
        const double* arow = A + i * K;
        double* crow = C + i * N;
        for (index_t k = 0; k < K; ++k) {
            const double a = arow[k];
            const double* brow = B + k * N;
            for (index_t j = 0; j < N; ++j) {
                crow[j] += a * brow[j];
            }
        }
    }
}

void matmul_tiled(
    const double* A, const double* B, double* C,
    index_t M, index_t K, index_t N,
    index_t BM, index_t BK, index_t BN
) {
    std::fill(C, C + M * N, 0.0);
    for (index_t ii = 0; ii < M; ii += BM) {
        const index_t i_end = std::min(M, ii + BM);
        for (index_t kk = 0; kk < K; kk += BK) {
            const index_t k_end = std::min(K, kk + BK);
            for (index_t jj = 0; jj < N; jj += BN) {
                const index_t j_end = std::min(N, jj + BN);
                for (index_t i = ii; i < i_end; ++i) {
                    const double* arow = A + i * K;
                    double* crow = C + i * N;
                    for (index_t k = kk; k < k_end; ++k) {
                        const double a = arow[k];
                        const double* brow = B + k * N;
                        for (index_t j = jj; j < j_end; ++j) {
                            crow[j] += a * brow[j];
                        }
                    }
                }
            }
        }
    }
}
~~~

تُضاف دالة dispatch أعلى النواتين، وتختار baseline للحالات الصغيرة وtiled للحالات التي تثبت القياسات فائدتها. احرص على التحقق من الأبعاد وأحجام التخزين قبل الدخول إلى أي نواة، كما تفعل واجهة `cpp_matmul` الحالية. لا تكرر التخصيص أو تصفير الناتج داخل الحلقات؛ أنشئ مخزن الناتج مرة واحدة وصفّره مرة واحدة.

**تنبيه:** الكود أعلاه يستخدم `M * N` في التعبير الخاص بملء الناتج للتوضيح. التنفيذ الفعلي يجب أن يستخدم نتيجة فحص الحجم الآمن الموجودة بالفعل في المحرك، حتى لا يصبح الحساب نفسه مصدر overflow.

### المرحلة C — تقليل التخصيصات وKernel Fusing

- سجّل عدد التخصيصات والنسخ في forward وbackward وoptimizer قبل محاولة إزالتها.
- أعد استخدام scratch buffers ذات السعة الكافية بدل إنشاء vectors مؤقتة في كل نداء. اربط عمر كل مخزن بخطوة التدريب، ولا تسمح بتداخل أو إعادة استخدام buffer ما زال مطلوبًا للـ backward.
- وسّع استخدام مخزن الذاكرة المؤقت الحالي فقط بعد اختبار إعادة الدخول وتعدد الخيوط؛ المورد المحلي للخيط لا يعني أن كل مخزن بيانات آمن للمشاركة.
- افحص عمليات يمكن دمجها دون تغيير رياضي، مثل bias مع dense output، أو تفعيل بسيط مع ناتج الطبقة، إذا كان الدمج يخفض المرور على الذاكرة والتخصيصات بالفعل.
- لا تنشئ نسخة جديدة من العمليات داخل `cpp_matmul` ثم تفترض أن مسار `transformer_train_batch` يستعملها. قِس المسار المدمج، وحدد موضع الحساب الحقيقي، ثم حسّن ذلك الموضع.
- لا تجمع تحديثات optimizer لكل micro-batch بصورة مستقلة إذا كان المطلوب الحفاظ على نتيجة التحديث الحالي. عند الحاجة إلى micro-batching، اجمع التدرجات أولًا ثم نفّذ تحديثًا واحدًا، مع وزن صحيح حسب عدد أهداف التدريب الفعلية.

### المرحلة D — تثبيت تمثيل السياق

- أبقِ Level 2 على token IDs ثم lookup إلى `token_embedding`، وأضف position embeddings ضمن التمثيل الكثيف الصغير `context_length × d_model`.
- لا تُحوّل كل token إلى متجه One-hot بطول vocabulary؛ هذا يرفع الذاكرة والعمل بلا فائدة مقارنة بالـ embedding lookup.
- افحص المسارات القديمة في Level 1 أو أي data encoder يستخدم one-hot أو مصفوفة ميزات كثيفة، واحتفظ بواجهة توافقية عند الحاجة بدل تغيير جميع checkpoints مرة واحدة.
- في backward، قيّم تحديث صفوف embeddings التي ظهرت فقط في العينة، مع مراعاة تجميع التدرجات عند تكرار token نفسه، ووزن الهدف وقواعد optimizer الحالية. لا تعتمد تحديثًا sparse قبل مقارنته بالتحديث الكثيف على حالات صغيرة حتمية.
- اختبر حفظ checkpoint وإعادة تحميله وتطابق token IDs، وحجم vocabulary، وأسماء وأشكال embeddings.

### المرحلة E — Validation والتعميم والنص المولّد

التدريب يجب أن يحتفظ بمقاييس منفصلة على الأقل لـ:
- `train_loss`
- `language_validation_loss`
- `dialogue_validation_loss`
- `response_focused_validation_loss` عندما توجد عينات كافية
- `validation_loss` المستخدم لاختيار أفضل checkpoint وإيقاف التدريب المبكر.

إجراءات مطلوبة:

1. تأكد أن فصل بيانات التحقق يتم على مستوى المصدر أو المحادثة قبل تقطيع النص إلى windows؛ لا تسمح بوقوع أجزاء متداخلة من المحادثة نفسها في التدريب والتحقق.
2. تأكد أن `evaluate` لا يغيّر أوزان النموذج ولا يستدعي optimizer step.
3. بعد كل epoch، ولعدد صغير ثابت من prompts عربية وإنجليزية، ولّد عينات فعلية بإعدادات deterministic مثل temperature=0، وسجّل النصوص مع checkpoint والـ seed والإعدادات.
4. قيّم العينات بقائمة مراجعة ثابتة: ملاءمة السؤال، اتساق السياق، عدم تكرار الإجابة بصورة مفرطة، سلامة العربية/الإنجليزية، وعدم ادعاء معرفة غير موجودة. هذه المراجعة لا تستبدل validation loss، لكنها تكشف حالات لا يظهرها loss وحده.
5. احفظ checkpoint الأفضل بحسب validation loss؛ احتفظ أيضًا بنتائج التوليد للمقارنة بين الإصدارات. لا تُعلن تحسن المحادثة من انخفاض train loss وحده.

### المرحلة F — Benchmark شامل End-to-end

احتفظ بقياس منفصل لكل من:

- GEMM فقط: baseline مقابل tiled على أشكال متعددة.
- forward فقط.
- loss فقط إن أمكن قياسه دون تكاليف تحويل بيانات غير ممثلة في المسار الحقيقي.
- backward فقط.
- optimizer فقط.
- خطوة تدريب كاملة (forward + loss + backward + optimizer).
- تدريب batch المدمج `transformer_train_batch`.
- توليد token واحد وتوليد رد قصير بطول ثابت.
- ذروة الذاكرة أو حجم workspace وعدد التخصيصات إن أمكن قياسها بصورة ثابتة.

يجب أن يتضمن التقرير: الجهاز ونظام التشغيل والمترجم وإعدادات البناء، أبعاد النموذج والسياق وvocabulary والـ batch size، warmup، عدد التكرارات، وسيط الزمن، أمثلة/ثانية، loss قبل التدريب وبعده، ودقة الفرق العددي. اختبر batch sizes صغيرة ومتوسطة، ولا تقارن نتائج بأعداد steps أو أطوال sequences مختلفة.

## 4. الاختبارات المطلوبة قبل قبول أي تحسين

- صحة الأبعاد وحدود tile، بما فيها الأبعاد غير القابلة للقسمة على tile.
- مقارنة baseline مقابل optimized على حالات حتمية، بسماحية مطلقة ونسبية معلنة.
- اختبارات gradient / finite-difference على نموذج مصغر جدًا لعدد محدود من المعلمات.
- مقارنة خطوة training واحدة: loss، gradient summaries، والأوزان بعد optimizer.
- اختبار حفظ checkpoint واستعادته، ثم مقارنة validation metrics وعينات التوليد.
- مجموعة الاختبارات الحالية كاملة، وليس الاختبارات الجديدة وحدها.
- إعادة قياس end-to-end على الجهاز المستهدف؛ لا يكفي نجاح benchmark النواة منفردة.

احفظ مخرجات التشغيل قبل أي تعديل. بعد إضافة النواة الجديدة، أعد نفس الأوامر على نفس الجهاز والإعدادات، ثم أضف اختبار مقارنة baseline/النواة المحسّنة. لا تقبل التغيير إلا بعد مرور الاختبارات وظهور مكسب قابل للتكرار في خطوة التدريب الكاملة دون تراجع ملحوظ في validation أو جودة النص المولد.

## 6. ترتيب التنفيذ المقترح

1. تثبيت القياسات والاختبارات الحالية وإضافة تقرير benchmark مرجعي.
2. فصل baseline GEMM عن tiled، وإضافة مقارنة عددية، ثم dispatch مبني على القياس.
3. قياس الذاكرة المؤقتة والتخصيصات، وإعادة استخدام buffers ودمج العمليات ذات العائد المثبت.
4. حماية embedding-based context وإزالة أي One-hot كثيف متبقٍ في المسارات القديمة بعد اختبار التوافق.
5. توسيع فحوص validation والتوليد الفعلي وحفظ أفضل checkpoint.
6. قياس forward/backward/optimizer والتدريب المدمج والتوليد من البداية إلى النهاية، ثم قبول التحسينات على أساس النتائج.

**المبدأ النهائي:** صحة الرياضيات أولًا، ثم أداء النواة، ثم أداء التدريب/التوليد الكامل، ثم التعميم. لا يتم استبدال المسار المرجعي حتى تتجاوز كل بوابات القبول.
